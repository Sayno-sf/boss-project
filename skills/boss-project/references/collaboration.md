# 经理如何协调一轮工作

开工时把第一项可验证的结果写进 `boss_stage.policy.firstProof`。如果有一个会影响交付的未知，写进 `uncertainty`。例如“先让一个人从入口走到第二厅，看看他能否看懂第一个岔口”。技术员可以同时陪老板了解这条路线。

新阶段显式传入 `policy`，空对象也会启用双项审查和失败返工。已有阶段沿用建阶段时的约定。默认每次派一批。有两个确实互不妨碍的任务时，经理可设 `maxParallel: 2`，并在各自的 `boss_assign.scope` 列出具体项目相对路径，例如 `{"read":["requirements/route.md"],"write":["guide/route.md"]}`。多个员工可以共读同一材料。有交叉写入、共用同一聊天、未声明范围，或需要访问范围不明的产物时，按顺序做。路径声明用于派工协调；共享数据库、外部服务、链接或会变化的路径请独占。需要扩展范围时先让经理安排时序。

经理领取一项后向返回的原聊天投递，拿到真实轮次后登记 `boss_sent`。并行阶段继续领取到 `blocked` 或 `empty`，用宿主等待这些轮次中最先完成的一项，凭该轮的真实原文结案，再领取。不要等待慢任务才给已经空闲的员工派活。实际采用的模型、上下文和证据可从 `boss_task_trace` 查到。

老板的明确决定用 `boss_agreement` 登记原话出处，`roles` 可限定适用成员，空列表由全队共用。替代旧决定使用新 ID 和 `supersedes`，适用成员保持一致。下一次认领会带上现行决定。已经开工的员工通过 `boss_team_board` 可查新决定；若变更影响手头工作，经理应及时向原聊天说明。决定记录引用权威批示或文档，不更改阶段授权。

有明确项数预算时，把 `workLimit` 设为本阶段获准登记的工作任务数。失败修复和复测也各占一项，讨论和独立审查不占。用尽后经理向老板解释额外工作及原因。根据真实追加授权，由所有者入口 `raise-limit` 登记 `stageId, workLimit, opinion, sourceRef`。余额允许时等待的返工会恢复。此数字表示任务数；若收到的是金额或用时预算，要单独记录并据实跟踪。

工程任务用 `handoff.to` 指定验证员。验证员的任务用 `fromJob` 接实际交付，并带上 `feedbackIds`。归档验证员的失败回执后，会生成给原实现员工的修复任务。修复归档后再回到原验证员，使用原场景实测新版本。两次自动修复后仍失败、来源不明或额度不足时，`boss_team_board.pending` 显示需要经理处理的问题。先查 `boss_task_trace` 和证据再作判断。未测记录保留在审查材料中。正式报告前，原审查员分别核对需求和质量，写下证据。

飞书上，已配对老板单独发送 `/团队` 或 `/任务 任务编号`，接收程序按已登记事实直接答复。查询中的“没有已登记的在办任务”描述的是项目台账。需要解释或批示时，按原有方式找经理或使用正式卡片。
