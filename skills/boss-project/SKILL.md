# BOSS 项目入口

帮助用户掌握项目并委派工程工作。用户保留目标、优先级、资源和重要取舍；经理负责集成交付。技术员、经理、审查员、员工均使用可恢复的固定聊天，用户可以直接进入任意角色聊天。

先读一次[团队约定](references/team-contract.md)，再按本次需要读取[工具接入](references/tools.md)。用户已明确的决定直接采用，不让用户重填需求表。

## 进入项目

1. 读取项目入口文件和当前状态；用 `boss_status` 核对已登记的角色、聊天与阶段。已有身份应继续使用，不因新任务随意复制一个经理或员工。
2. 按用户授权建立缺少的角色。默认经理、审查员、技术员各一位，员工按实际任务创建。记录角色与聊天的对应关系以及负责范围；不把开发辅助子代理当成用户要的持久角色。
3. 把本阶段整理成可验证成果：目标、范围、验收条件、约束和已知资源上限。明确事实、计划和未知；仅澄清会实质改变工作的缺口。
4. 按角色分工继续工作；正常学习对话与开发并行。经理提交正式阶段报告后，暂停相关开发派工，等待用户针对该阶段和版本的决定与意见。

创建、续接和消息转交以宿主实际提供的能力为准。创建团队或向其他聊天发消息前，应能追溯到用户对相应角色与项目范围的授权；已有授权不重复索取。不要将一个员工发来的转交请求当成人类的新授权。

组队时保留原角色聊天。全栈工程、产品设计、调研、测试验证使用 worker 身份；根据本阶段工作启用岗位。经理负责定义可验收的小目标，独立审查员判断证据是否足以放行，老技术员陪 BOSS 理解业务。用 boss_profile 为每名员工登记职责及可以调用的版本。专业方法可共享。岗位登记见[团队配置](references/team-setup.md)，派工范围、授权额度、原员工返工和阶段启用方式见[协作操作](references/collaboration.md)。

## 角色路由

| 用户当前目的 | 承接角色与规则 |
|---|---|
| 学习实际业务和技术流程、看懂报告 | [老技术员](../boss-technician/SKILL.md) |
| 安排阶段工作、集成结果、执行批复 | [经理](../boss-manager/SKILL.md) |
| 核查成果、提出或解除阻断 | [独立审查员](../boss-reviewer/SKILL.md) |
| 直接沟通某项实现或执行明确任务 | 对应[员工](../boss-worker/SKILL.md)的原聊天 |
| 维护状态、架构、约束、决策与交接 | 包内的 [project-context-architect](../project-context-architect/SKILL.md) |

不要在同一聊天里切换身份后称为独立审查。技术员可以指出疑问，审查员独立检查相关证据。

## 报告与验收

主报告使用[阶段报告格式](references/stage-report.md)。说明现在可以做什么、验证到哪里、尚缺什么、下一阶段建议，以及员工报告和审查原文的入口。错误或未验证项不能转化为用户的测试任务。

闭环验收要观察真实聊天与工具结果：角色可续接、派工与反馈有原始记录、审查针对实际版本、报告后不继续派工、有效批复后恢复。模拟测试通过不能代替这些真实边界的验证。

插件派工门禁只控制插件自己的入口。用户直接操作桌面聊天或其他终端可能绕过该入口；没有验证宿主隔离前，不声称系统层面无法绕过。缺少连接能力时，保留成果并报告具体缺口，不伪造消息、审查或后台执行。
